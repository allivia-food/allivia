ALLIVIA — SUPABASE AUTH COM ENVIO PELO RESEND

1. CONFIGURAÇÃO DO APLICATIVO

No .env local e nos ambientes preview e production do Expo/EAS, configure:
EXPO_PUBLIC_SUPABASE_URL=URL_DO_PROJETO
EXPO_PUBLIC_SUPABASE_ANON_KEY=CHAVE_PUBLICA_DO_PROJETO

Não use service_role ou credenciais SMTP no aplicativo.
Mantenha DEV_SIMULATED_SESSION = null.

2. CONFIGURAÇÃO NO SUPABASE

Abra Authentication > Sign In / Providers > Email:
- Ative Email e permita novos cadastros.
- Ative Confirm email.
- Configure Email OTP length: 6.
- Configure Email OTP expiration: 600 segundos (10 minutos).
- Configure senha com mínimo de 8 caracteres, incluindo letra e número.

Sem Confirm email, o cadastro entra diretamente e não envia confirmação.
Não é necessário criar tabelas de códigos ou novas migrations.

3. CONFIGURAR O RESEND

O fluxo será: aplicativo > Supabase Auth > SMTP do Resend > destinatário.
O Supabase continua gerando e validando os códigos; o Resend entrega os
e-mails. Não é necessário alterar o código do aplicativo para usar SMTP.

3.1. Verificar um domínio

- Acesse https://resend.com e crie ou entre na sua conta.
- Em Domains, adicione um domínio que você controla. Pode usar um
  subdomínio exclusivo para os e-mails do app, como auth.example.com.
  Esse é apenas um exemplo: substitua pelo seu domínio real.
- No painel que gerencia o DNS desse domínio, adicione os registros
  exibidos pelo Resend para autenticação do envio (SPF e DKIM).
  Use exatamente os tipos, nomes e valores mostrados no painel.
- Não apague registros de e-mail existentes para copiar os exemplos.
  Configure somente os registros necessários ao domínio/subdomínio usado.
- Volte ao Resend, solicite a verificação e aguarde o status Verified.
- Para este fluxo, basta habilitar o envio; não é necessário configurar
  recebimento de e-mails no Resend. DMARC é uma melhoria recomendada
  para autenticação e reputação do domínio.

Para enviar a usuários reais, é necessário verificar um domínio próprio.
Um endereço Gmail/Outlook não serve como domínio remetente verificado.
Confira as cotas do plano do Resend; SMTP também está sujeito a limites.

3.2. Criar uma chave de API

- Em API Keys, crie uma chave para o Supabase, por exemplo Allivia Auth.
- Prefira permissão de envio (Sending access), restrita ao domínio usado.
- Copie e guarde a chave em local seguro. Ela será a senha SMTP.
- Não coloque essa chave no .env do app, em EXPO_PUBLIC_*, no Expo/EAS,
  nos templates ou no código-fonte. Não use a senha da sua conta Resend.

3.3. Conectar ao Supabase

No projeto Supabase, abra Authentication > Email > SMTP Settings
(a posição do menu pode variar) e ative Custom SMTP.
Preencha:

Sender name: Allivia
Sender email: um endereço no domínio verificado no Resend
Host: smtp.resend.com
Port: 465
Username: resend
Password: sua chave de API do Resend
Encryption, caso exista o campo: SSL/TLS para a porta 465

Exemplo de remetente: no-reply@auth.example.com, somente se você verificou
auth.example.com. Substitua pelo seu domínio real. Verificar um subdomínio
não autoriza automaticamente um remetente no domínio principal.

Salve. O remetente não precisa ser uma caixa postal para este envio,
mas deve pertencer ao domínio verificado e autorizado pela chave.
As credenciais do Resend ficam somente na configuração SMTP do Supabase.

3.4. Limites e rastreamento

- Em Authentication > Rate Limits, ajuste os limites de e-mail do Supabase
  à cota disponível no Resend. Trocar o SMTP não remove esses limites.
- Mantenha o intervalo de reenvio de pelo menos 60 segundos no servidor;
  o app também bloqueia o botão de reenvio por esse intervalo.
- Desative rastreamento de cliques e aberturas para estes e-mails de
  autenticação, nas configurações do domínio no Resend.
- Os três templates continuam instalados no SUPABASE, conforme a seção 4.
  Não é necessário cadastrá-los em Resend Templates.
- Não configure Send Email Hook, Edge Function ou webhook para este fluxo.
  Se já houver um Send Email Hook ativo, confira-o: este manual considera
  o envio nativo do Supabase por Custom SMTP, sem hook substituindo o envio.

4. INSTALAR OS TRÊS TEMPLATES

Abra Authentication > Email Templates.
Abra cada arquivo HTML no VS Code ou Bloco de Notas, copie todo o
código-fonte e cole no corpo do modelo correspondente no Supabase.

CADASTRO
Modelo no Supabase: Confirm sign up
Arquivo: supabase/email-templates/confirm-signup.html
Assunto: Confirme seu cadastro no Allivia

RECUPERAÇÃO DE SENHA
Modelo no Supabase: Reset password
Arquivo: supabase/email-templates/reset-password.html
Assunto: Seu código para recuperar a senha do Allivia

ALTERAÇÃO DE SENHA NO PERFIL
Modelo no Supabase: Magic Link
Arquivo: supabase/email-templates/magic-link.html
Assunto: Confirme a alteração de senha no Allivia

O perfil usa o endpoint OTP do Supabase, cujo e-mail utiliza o modelo
Magic Link. Por isso, cole o terceiro template em Magic Link, e não em
Reauthentication. O template envia um código, sem link de login.

Preserve exatamente {{ .Token }} nos três templates.
Não substitua por TokenHash, ConfirmationURL ou por um número fixo.
Salve os três modelos no painel.

5. FUNCIONAMENTO

Cadastro: criar conta > confirmar código > personalizar perfil.
Recuperação: informar e-mail > confirmar código > definir e confirmar
nova senha > voltar ao login.
Perfil: preencher nova senha e senha atual > Salvar > confirmar o código
enviado ao e-mail atual da conta > gravar as alterações.

Os códigos são validados pelo Supabase. A recuperação usa uma sessão
temporária separada da sessão normal. Se fechar o app antes de definir
a senha, será necessário verificar outro código.

A etapa de código é exigida pelos fluxos implementados no app; ela não
altera as políticas globais da API pública de atualização de usuário.
Se outra operação do perfil falhar após atualizar a senha, essa falha
não desfaz a troca de senha já concluída.

6. TESTAR

- Crie uma conta e confirme com o código recebido.
- Teste um código errado, expirado e iniciado por zero.
- Teste o reenvio após 60 segundos.
- Recupere a senha e confira o login com a senha nova.
- No perfil, confirme que a senha não muda antes do código correto.
- Cancele a verificação do perfil e confira que nada foi salvo.
- Em Resend > Emails, confira se o e-mail aparece e seu status de entrega.
  Confirme também o recebimento na caixa de entrada ou no spam.
- Se o e-mail não aparecer no Resend, consulte os logs de Auth do Supabase
  e confira SMTP, chave, remetente e limites de envio.
- Se aparecer como rejeitado ou devolvido, confira o motivo no Resend,
  o domínio verificado, o destinatário e as cotas da conta.

Se receber links em vez de códigos, confira os modelos e {{ .Token }}.
Se o código tiver mais de seis dígitos, corrija Email OTP length.
Se os e-mails não chegarem, confira SMTP, limites, destinatário e spam.
Um projeto com CAPTCHA ativado exige a integração de captchaToken;
os formulários atuais ainda não incluem essa etapa.

O código e os arquivos estão preparados. A configuração do projeto remoto
e a entrega real dos e-mails precisam ser testadas após estes passos.

7. O QUE É ADICIONAL E O QUE NÃO PRECISA MUDAR

Adicional: verificar o domínio via DNS, criar a chave no Resend, configurar
Custom SMTP, conferir limites e testar a entrega real dos três fluxos.

Não é necessário instalar SDK do Resend no app, criar tabelas de códigos,
criar uma Edge Function, usar uma chave administrativa do Supabase ou
gerar nova build apenas por trocar o provedor SMTP. As telas e os fluxos
de autenticação já implementados precisam estar na versão instalada.

Verifique as condições e cotas atuais do Resend. Não é necessário
contratar um plano pago se a cota disponível atender ao seu uso; possuir
ou registrar um domínio é uma questão separada do plano de envio.
